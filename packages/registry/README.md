# @kleisis/registry

`@kleisis/registry` reads a schema registry generated by Kleisis, in the format `kleisis:schema-registry@2`, from TypeScript. On every registry, the package gives the verdict of the Python reader `kleisis.registry.read_registry`. The package imports no Node module, so it also runs in Obsidian on mobile. Its only dependency is `yaml`.

## Usage

The caller passes the text of the registry file and, optionally, the path of that file. The error messages name that path:

```typescript
import { readRegistry, RegistryError } from "@kleisis/registry";

try {
  const registry = readRegistry(text, ".kleisis/registry.yml");
  // registry.version, registry.schemas, registry.exports, registry.resources, registry.keywords
} catch (error) {
  if (error instanceof RegistryError) console.error(error.rule, error.message);
}
```

Two further functions check a contract identifier `<namespace>:<name>@<version>`. First, `isContractIdentifier` tells whether a text follows the grammar. Second, `parseContractIdentifier` splits an identifier into its parts. The constant `REGISTRY_FORMAT` holds the format identifier `kleisis:schema-registry@2`.

## Verdicts

Each `RegistryError` carries the rule that the Python reader names in its finding:

- `registry/invalid`: the file cannot be read as YAML, it violates the registry format, or a path is not a non-empty string;
- `contract/identifier`: a key of `schemas` or an entry of `exports` departs from the grammar of a contract identifier;
- `path/escape`: a path is absolute, holds a segment `..`, or names the root of the repository.

The package parses YAML as PyYAML parses it: in YAML 1.1, without duplicate keys or merge keys `<<`. For example, a plain `yes` is a boolean, whereas a plain `y` or `1e3` is a string. Both readers pass the conformance cases of [`specs/cases/registries.yml`](../../specs/cases/registries.yml) and [`specs/cases/contract-identifiers.yml`](../../specs/cases/contract-identifiers.yml).

## Installation

Each release of Kleisis attaches the package as a tarball, since npm installs no subdirectory of a Git repository. A consumer pins the tarball by its URL in its file `package.json`:

```json
{
  "dependencies": {
    "@kleisis/registry": "https://github.com/esther-poniatowski/kleisis/releases/download/v<version>/kleisis-registry-<version>.tgz"
  }
}
```

After the command `npm install`, the lockfile of the consumer records the integrity hash of the tarball, and the command `npm ci` refuses a tarball whose bytes differ from that hash. The command below computes the hash of a tarball in the form recorded by the lockfile, so that the hash can be checked against the release before the lockfile adopts it:

```sh
curl -sL <tarball-url> | openssl dgst -sha512 -binary | base64 | sed 's/^/sha512-/'
```

During joint development, a consumer points at a local clone of Kleisis instead. The package exports its build output, so the commands below build the package in the clone, then install it in the consumer:

```sh
npm --prefix ../kleisis/packages/registry install
npm --prefix ../kleisis/packages/registry run build
npm install ../kleisis/packages/registry
```

## Development

The scripts run from this folder, after `npm install`:

```sh
npm run typecheck
npm run lint
npm run format:check
npm test
npm run build
```

The tests read the cases and the schemas of `specs/` at the root of the repository, without a copy.
